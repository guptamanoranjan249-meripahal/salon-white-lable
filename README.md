# Nexora Salon Studio

A white-label salon website builder. Every salon owner gets a private workspace, a configurable public website, and a separate booking inbox. The application starts with empty tenant content—there are no seeded salons, services, staff, customers, or bookings.

## What is included

- Owner registration and sign-in with a private, HTTP-only session cookie.
- One isolated salon workspace per owner. Owner APIs scope every salon update and booking query to the authenticated account.
- A guided dashboard for website name and URL, logo, hero image, services and prices, staff, colors, homepage copy, contact details, social links, and opening hours.
- Private draft saving, a preview of the exact draft, and explicit publish/unpublish actions. Saving a draft does not change the currently published website; publishing replaces the live version.
- Path-based public addresses by default (`https://yourdomain.com/your-salon`). Wildcard subdomain routing is supported when `PUBLIC_BASE_DOMAIN` and the matching DNS/TLS setup are configured.
- A public service menu and appointment-request form. Requests are persisted and visible only to that salon owner.
- Locally stored JPG, PNG, WEBP, and GIF image uploads, limited to 5 MB each. Secure HTTPS image URLs are also accepted.
- Responsive layouts for the marketing site, owner workspace, and public salon site.

## Requirements

- Node.js **22 or newer** (the production API uses `better-sqlite3`).
- npm 10 or newer.

## Run locally

```bash
cp .env.example .env
npm install
npm run dev
```

Open <http://localhost:3000>. Register an owner account, add your own content in the dashboard, preview it, then publish. No demo tenant is created automatically.

Useful commands:

```bash
npm run lint       # Type-check the frontend and server
npm test           # API integration tests
npm run build      # Build the browser application
npm start          # Serve the production build and API
npm run preview    # Build and start the production server
```

The development server hosts both the Vite frontend and the API on port 3000, so the browser uses same-origin API requests and session cookies.

## Production configuration

Copy `.env.example` into your deployment environment and set:

- `NODE_ENV=production`
- `PORT` to the port supplied by your host
- `DATABASE_PATH` to a writable, persistent SQLite file location
- `UPLOADS_DIR` to a writable, persistent image directory
- `PUBLIC_BASE_URL=https://yourdomain.com` for path-based URLs, **or** `PUBLIC_BASE_DOMAIN=yourdomain.com` for wildcard salon subdomains
- `TRUST_PROXY=true` only when traffic is behind a proxy you control

Build and start with `npm run build` and `npm start`. The application binds to `0.0.0.0`.

### Public domains

For path-based websites, route the domain to this application and keep `PUBLIC_BASE_URL` set to its HTTPS origin. A salon is available at `/{slug}` after it is published.

For subdomains, point a wildcard DNS record (`*.yourdomain.com`) to the application, provision a TLS certificate that covers the wildcard, set `PUBLIC_BASE_DOMAIN=yourdomain.com`, and route those hosts to the same service. The public resolver uses the first-level subdomain as the published salon slug. Keep a platform/marketing site at the base domain separately if desired.

### Storage and backups

SQLite and uploaded images are durable only when `DATABASE_PATH` and `UPLOADS_DIR` point to persistent storage. Back up the database and upload directory together. This configuration is designed for a single application instance; do not run multiple replicas against separate local disks. For a horizontally scaled deployment, move tenant and booking storage to a managed shared database and uploads to shared object storage before adding replicas.

## Security and tenancy notes

- Passwords are stored as salted scrypt hashes. Session tokens are random, only their hashes are stored in SQLite, and the browser cookie is `HttpOnly` and `SameSite=Lax` (and `Secure` in production).
- Mutating API requests reject cross-origin browser requests. Authentication and public booking endpoints have basic per-process rate limits.
- Public salon responses contain only the published website snapshot; drafts and owner details are not exposed publicly.
- Image upload paths are owner-scoped and filenames are generated by the server. Validate reverse-proxy configuration and use HTTPS in production.
- Email delivery (verification, password reset, booking notifications) is not configured in this repository. Booking requests are stored in the owner workspace; connect a transactional email provider before relying on email notifications.
